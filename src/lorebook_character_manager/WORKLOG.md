# 世界书角色平台工作日志

## 2026-08-20：模板条目与返回自检方案确认

### 本次确认的产品语义

1. 世界书中的“人物创建模板”等条目可以保持关闭。
2. 关闭的模板条目在日常聊天中不应被扫描、激活或发送给主聊天模型。
3. 只有用户打开“世界书角色平台”，选择模板并主动发起角色创建时，脚本才读取该条目的 `content`。
4. 读取后的模板正文由脚本显式拼入这一次 `generate()` 请求，而不是临时打开世界书条目。
5. 生成结束后，结果应先经过本地自检，通过后才能作为可注入的人物档案使用。

### 当前实现状态

- 已支持选择任意世界书及其中的指定条目作为人物创建模板。
- 读取模板时直接调用 `getWorldbook()` 获取条目内容，不依赖条目的 `enabled` 状态。
- 不会为了生成而打开模板条目，因此关闭模板不会污染日常聊天。
- 模板正文、提取后的最近聊天记录和用户要求，会显式组合进单次生成请求。
- 当前已有宽松的 XML 标签提取：优先读取 `<character_profile>` 或 `<人物档案>`；没有匹配时会回退到完整回复。

### 待定：LLM 返回内容严格自检

暂不实现，后续确认输出协议后再加入。建议流程：

1. 保存模型的原始返回内容，避免校验失败后丢失排查依据。
2. 严格检查要求的 XML 根标签是否存在、是否成对闭合、是否只出现允许的数量。
3. 从指定标签中提取正文，不再在严格模式下自动回退到完整回复。
4. 如果模板要求 JSON，则执行 `JSON.parse()`。
5. 使用 Zod 校验 JSON 字段、类型、必填项及允许值，并用 `z.prettifyError()` 生成可读错误。
6. 校验失败时不注入世界书，UI 显示具体错误、保留原始回复，并提供“按原要求重 ROLL”和“加入修改意见重 ROLL”。
7. 校验通过后才进入草稿编辑与临时世界书注入步骤。

### 尚待决定的问题

- 输出协议是全局统一，还是由每个模板条目分别声明。
- XML 标签名称是否固定，或允许用户在 UI 中设置。
- JSON Schema 是内置、由 UI 配置，还是放在另一个世界书条目中。
- 校验失败是否允许用户忽略警告并手动采用原始回复。
- 是否增加一次自动修复请求；目前倾向默认只报错，由用户决定是否重 ROLL，避免额外 API 消耗。

### Git 状态

- 本节记录时仅完成了设计与待办整理；相关内容随后与功能代码一并纳入本轮提交。

## 2026-08-20：聊天历史 XML 提取与楼层过滤

### 已实现

- 扫描用户指定的最近 N 个有效楼层，自动列出其中实际存在且成对闭合的 XML 标签及出现次数。
- 用户可点击检测到的标签，自行加入或移出当前规则。
- 提供两种互斥模式：
  - 白名单：只提取所选标签内部的内容；没有匹配标签的楼层不会发送。
  - 黑名单：从原始消息中移除所选标签及其完整区块，再发送剩余正文。
- 默认白名单加入 `content`、`novel`、`正文`、`maintext`、`story`、`response`。
- 默认黑名单加入
  `think`、`thinking`、`reasoning`、`update`、`updatevariable`、`UpdateVariable`、`Analysis`、`JSONPatch`、`StatusBlock`、`status`。
- 最近楼层数量允许设置为 0–1000。
- 先从完整聊天记录中排除隐藏楼层和非目标身份，再截取最后 N 楼，避免隐藏/system 楼层占用数量。
- 默认只使用 user 与 assistant 楼层；用户可选择包含 system 楼层。
- 读取 `getChatMessages()`
  返回的原始聊天记录，不调用显示格式化或酒馆正则格式化接口，因此不会主动套用显示正则、提示词正则。

### 已知边界

- 酒馆没有为所有第三方脚本创建的消息提供统一、可靠的来源标识。其他脚本若创建的是隐藏或 system 楼层，会被默认过滤；若伪装成普通、可见的 user/assistant 楼层，则无法仅凭通用消息字段可靠排除。
- 如果某个正则或脚本已经永久改写了聊天文件中的原始消息，而不只是显示/提示词阶段替换，脚本只能读取改写后的内容。
- 自动检测只列出成对 XML 标签；未闭合的流式标签不会被当作可选正文标签。

## 2026-08-20：角色记忆缓存与增量版本

### 已实现

- 脚本创建和维护的角色条目带有版本号、聊天 ID、更新时间楼层及计划删除楼层元数据。
- 条目名称显示为“角色记忆 · 角色名 · vN（更新于 X 楼）”。
- 每个聊天缓存最后更新楼层、下次检查楼层、更新间隔和版本历史。
- 用户可对当前聊天的角色档案开启自动更新，并设置间隔 Y（1–1000 楼）。
- 完全静默模式：到达检查楼层后在后台生成并写入新版本。
- 感知模式：更新前弹出确认，显示角色名及已经过去的楼层数；拒绝后延后一个完整更新间隔再询问。
- 是否更新完全由脚本机械判定：用户点击“立即更新”，或当前楼层达到用户设置的下次更新楼层。
- LLM 不参与是否更新的决策；任务触发后只读取上次更新楼层之后的新剧情，并返回完整的最新版档案。
- 新版本使用新的世界书条目；写入成功后打开新条目、关闭旧条目，不覆盖旧内容。
- 旧版本记录 `新版本创建楼层 + 10` 为删除楼层；到达后从世界书及缓存版本链中永久移除。
- 监听消息接收来触发自动更新；消息删除、编辑和重 ROLL 只执行到期清理检查，不会额外调用模型。
- 切换聊天时仍按原设计卸载旧聊天的物化条目；返回聊天时根据缓存版本链恢复未过期版本，只有最新版打开。

### 兼容与安全顺序

- 旧缓存会自动补齐新增字段，并把原档案迁移为 v1。
- 更新顺序为：先成功创建并打开新条目，再关闭旧条目，最后更新缓存状态。
- 生成或写入失败时不会提前删除旧版本。
- 楼层回退不会自动重新打开旧条目；延迟 10 楼保留主要用于重 ROLL、回退后的人工排查和恢复余量。

### 暂有限制

- 当前每个聊天维护一份主要角色档案及其版本链；多角色并行维护需要后续把缓存从单档案升级为档案列表。
- 没有本地酒馆环境，弹窗返回值、实际世界书渲染和消息事件组合仍需实机点测。
- 本功能与前述变更已整理为同一轮 Git 提交；是否推送远端由用户另行决定。
